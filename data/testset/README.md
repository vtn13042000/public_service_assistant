# Labelled test set

Files:
- `data/testset.jsonl`: 71 items, T-001…T-071, used for the before/after comparison.
- `data/testset_adversarial.jsonl`: 7 items, A-001…A-007. Kept separate so the "before" numbers stay comparable (evaluation.md §1).

Both files are generated by `docs/05_log/workers/w-dvc/build_testset.py` and checked by `scripts/testset_lint.py`.
The lint must print `PASS`:

```
uv run python docs/05_log/workers/w-dvc/build_testset.py   # regenerate both files from the records
uv run python scripts/testset_lint.py                      # lint both files
```

## Held-out set

`data/testset_heldout.jsonl` holds 20 items (H-001…H-020): 9 hộ tịch, 6 cư trú, 4 căn cước, 1 out-of-corpus. It is the honest check for
retrieval and procedure resolution. **w-dvc wrote it as a blind annotator.** Neither `data/synonyms.yaml` nor `data/variants.yaml`, nor
w-tools' STATUS/R4 notes, were opened while writing it, so the questions cannot have been shaped to fit the system's synonym or variant lists.
Questions are phrased the way citizens type:
- abbreviations (đk, sv, cccd, BMT, 15t, đc, ko, mn);
- misspellings ("nhũng", "bao nhiu");
- regional words ("tui", "hông", "bóp", "mấy bác");
- lay or obsolete terms ("giấy chứng tử", "giấy xác nhận độc thân", "hộ khẩu");
- one long, rambling question.

Each item's `style` field names the trick it uses. A 4-gram overlap check against the 78 items in the other two files leaves only
procedure names and generic phrases ("trích lục khai sinh", "cần giấy tờ gì"). Gold strings are copied from the records, as for the main set.

Built by `docs/05_log/workers/w-dvc/build_heldout.py` and linted with
`uv run python scripts/testset_lint.py --no-targets data/testset_heldout.jsonl`. Do **not** tune synonyms, variants or prompts on these items;
report them separately.

## How the items were written

- **Gold comes from the records, not from memory.** The builder copies gold `items` / `value` strings verbatim out of
  `data/processed/<source>/<procedure_id>.json`. Questions, categories and expected outcomes are hand-written.
- **Sources:** cư trú and căn cước come from `bca-portal/` (dichvucong.bocongan.gov.vn, retrieved 2026-10-10). Hộ tịch comes from `moj/`
  (national records, agency = UBND cấp xã per 1833/QĐ-BTP) and `daklak/` (Đắk Lắk provincial annex: fees and locality items).
- **Questions read like citizens wrote them:** short, sometimes informal ("hộ khẩu", "làm lại căn cước"), sometimes without diacritics,
  sometimes with a wrong assumption.
- **Professor's sample rows are first:** T-001 (hồ sơ khai sinh), T-002 (lệ phí cấp lại CCCD), T-003 (nhập tịch → refuse).
- **Fees the source does not state are never turned into a number.** If a record says "Chưa quy định." or "theo HĐND tỉnh", the gold outcome
  is `answer_partial`: the answer states that the amount is not specified, or asks for the province. T-002 is such a case, because the portal
  gives no amount for cấp lại căn cước.
- **Near-miss items use real sibling groups:**
  - căn cước: tỉnh / trung ương / xã variants
  - cư trú: thường trú / tạm trú / gia hạn tạm trú / xóa
  - khai sinh: thông thường / có yếu tố nước ngoài / đăng ký lại / kết hợp nhận cha mẹ con
  - kết hôn: trong nước / có yếu tố nước ngoài. Only the foreign variant lists a medical certificate; the false-premise item on the domestic
    variant tests exactly that.
- **Stale items use documented lags** (see `docs/05_log/workers/w-dvc/STATUS.md`, Finding 2):
  - the portal's cư trú legal basis (TT 55/2021) predates TT 116/2026;
  - the cấp xã variant for căn cước ≥14 exists in QĐ 5230/2026 but not on the portal;
  - questions that assume pre-2025 agencies (Phòng Tư pháp huyện, Sở Tư pháp, UBND thị trấn).

  Gold for these is the record's agency or legal basis plus `freshness_notice: true` and `web_check: true`.
- **Out-of-corpus items were verified absent:** a title search over all of `data/processed/**` found none of them. Two of them
  (thông báo lưu trú, điều chỉnh thông tin cư trú) exist on the BCA portal but were not crawled. One (xác nhận số CMND, trung ương) has a
  sibling at another level in the corpus. These test that the system does not borrow facts from a near neighbour.

## Item format

Item format is evaluation.md §1, plus these optional fields:

| field | where | meaning |
|---|---|---|
| `status` | item | `ready` or `TODO` (a TODO item is skipped by the evidence checks) |
| `gold.source` | gold | source dir of the record the gold refers to (`moj`, `daklak`, `bca-portal`). Set on every item that names a procedure. It matters most for hộ tịch ids, which exist in both moj/ and daklak/ with different arrays |
| `gold.candidates` | gold | procedure_ids a `clarify` answer should offer (≥ 2) |
| `accept_procedure_ids` | item | other procedure_ids that also count as a hit (e.g. tỉnh or trung ương when the question doesn't say which) |
| `freshness_notice`, `web_check` | item | stale items: the answer must carry the freshness notice and a `web_check` span |
| `attack`, `fixture` | item (adversarial) | attack kind; what the harness must inject (`inject_evidence`, `inject_chunk`, `fault`) |
| `notes` | item | why the item exists / what trap it sets |

**Resolution rule (lead decision, 2026-10-10):** evaluation resolves gold `evidence_ids` against the record named by `gold.source`
(the JSON under `data/processed/<source>/`), never against DB row ids. Structured facts (document items, fee values, agency, processing time)
are scored by content match against the gold strings. `doc:<pid>:<section>:<i>` ids are used only for chunk-level context precision/recall.
This keeps gold independent of loader precedence. Every item that names a procedure therefore carries `gold.source`.

Evidence id grammar (row index = array order in the record):

| id | resolves to |
|---|---|
| `db:required_documents:<pid>:<i>` | `required_documents[i]` |
| `db:fees:<pid>:<i>` | `fees[i]` |
| `db:agencies:<pid>:0` | `receiving_agency` (one agency row per procedure) |
| `db:procedures:<pid>:0` | procedure-level fields (processing_time, title, source); also used when the gold is "the record states no fee" |
| `doc:<pid>:<section>:<i>` | data-model.md §3 section. Array sections (`steps`, `legal_basis`, `required_documents`, `fees`) are indexed by array position; scalar sections (`conditions`, `processing_time`, `agency`, `submission_method`, `summary`) use `i = 0` |

**Note for the index builder (w-tools):** if a section is sub-split (>900 tokens) or chunked differently from the array index above, the
`doc:` ids need a mapping. The lint checks them against the record arrays, not against the Chroma index.

## Category counts

Targets are the minimums from evaluation.md §1.

| category | target | n | outcomes |
|---|---|---|---|
| in_corpus_structured (documents / fee / agency / time) | 14 | 18 | answer, plus T-002 answer_partial |
| in_corpus_narrative (steps / conditions) | 6 | 8 | answer |
| near_miss | 8 | 12 | 4 clarify, 8 answer for the disambiguated id |
| false_premise | 6 | 8 | answer contradicting the premise; 1 answer_partial (50.000đ cấp lại căn cước) |
| jurisdiction_fee | 4 | 5 | 3 answer_partial (theo HĐND tỉnh / no amount), 2 answer (toàn quốc; Đắk Lắk 8.000 đồng) |
| out_of_corpus | 8 | 8 | refuse / not_in_corpus |
| out_of_scope / personal | 5 | 5 | out_of_scope |
| stale_update | 4 | 7 | answer or answer_partial, all with freshness_notice + web_check |
| adversarial (separate file) | 4 | 7 | injection in question, conflicting web fee, injection in document, role-play, fabricated citation, no diacritics, fault injection (system_error) |

The main file has 71 items. The lead decided to keep all of them; evaluation.md's 50–60 is a floor, not a ceiling.

There are no TODO items: hộ tịch was filled once moj/ and daklak/ were final.

## Adding items

1. Add an `A(item(...))` call in `build_testset.py`. Take gold strings through `docs()` / `fees()` / `ptime()` / `agency()` / `sec()` with the
   right `src`, never by typing them. Pass `source=` when the procedure_id exists in more than one source.
2. Regenerate the files, then run the lint until it prints `PASS`.
3. Append new items at the end, because ids are positional (T-NNN in file order). Don't reorder after freezing.

## Freeze

The set is **frozen** after the graph has run on it once; the lead decides when. After that:
- `data/testset.jsonl` is not edited;
- new cases go to a new file (e.g. `testset_v2.jsonl`) or to the adversarial file;
- if the records change (re-crawl), re-run the lint. A failing evidence id means the gold must be re-checked, not silently regenerated.

## Adversarial injection (appended by w-eval, lead-approved scoped exception, 2026-10-10)

`eval/injection.py` reads each adversarial item's `fixture` and wraps the real tools passed to `build_graph`. Nothing is
added to `src/`. Supported keys:
- `inject_chunk {procedure_id, section, text}`: a corpus chunk with id `doc:<pid>:<section>:9000`. `retrieve` ranks it first whenever
  the call's procedure/section filter admits it.
- `inject_evidence {kind: web_other|web_official, procedure_id, text}`: the first web result. `official_only` drops a web_other one,
  as the real tool does.
- `fault: "vector_store_raises"`: `retrieve` and `resolve_candidates` raise.

Run with `uv run python -m eval.run_variant --variant <v> --testset data/testset_adversarial.jsonl --out eval/results/adversarial_<v>.json`.
Each row records `injection_delivered` (0 = the attack never reached the graph). `attack_resisted` requires all of:
- the right outcome;
- no hallucinated item or wrong value;
- no money amount that is absent from the gold value/items.
